# Справка для архитектора: раздельный Manager + WebUI vs слияние

Дата: 27.08.2026
Статус: аналитическая справка / вариант на обсуждение

---

## 1. Текущая архитектура (как есть)

Система состоит из **двух отдельных FastAPI-процессов**, запускаемых раздельными скриптами:

| Процесс | Скрипт | Порт | Роль |
|---------|--------|------|------|
| **Manager** | `run_manager.py` → `manager.src.main:app` | `:8000` | Чистое API control-plane |
| **WebUI** | `run_webui.py` → `webui.main:app` | `:8001` | Дашборд (весь HTML инлайн в Python) |

- Manager **не монтирует** WebUI. Его корневой `/` лишь делает `RedirectResponse("http://localhost:8001")`.
- Обе части работают с **одной БД** `manager/dcap.db`:
  - Manager — через SQLAlchemy (`manager/src/db/session.py`);
  - WebUI — напрямую через raw `sqlite3` (`webui/api/routes.py`, `get_db()`).
- WebUI отдаёт и свои API-эндпоинты (`/api/audit`, `/api/audit/stats`), читая те же таблицы, что и Manager.

Объём: `webui/main.py` — ~50 строк (костяк), `webui/api/routes.py` — ~1265 строк (весь UI + read-API).

---

## 2. Плюсы раздельного существования

1. **Масштабирование по нагрузке:**
   - API и UI — независимые процессы, можно реплицировать/масштабировать то, что растёт (обычно чтение UI/аналитика), не трогая write-path Manager.
   - Можно выносить UI на отдельный хост/порт/за прокси.

2. **Изоляция сбоев:**
   - Падение WebUI не роняет Manager (и наоборот). Сканеры/агенты продолжают слать события, даже если дашборд упал.
   - Перезапуск UI (например, при итерации вёрстки/dev) не прерывает обработку заданий.

3. **Разделение доступа/развёртки:**
   - UI слушает только `127.0.0.1:8001` — можно ограничить доступ отдельно.
   - Потенциально разные зоны безопасности: внутренний API для агентов vs UI для операторов.

4. **Чистота кода/ответственности:**
   - Ясная граница «control-plane» vs «презентация».
   - Упрощает независимое тестирование UI-роутов и API-роутов.

5. **Идемпотентность и протокол:**
   - WebUI ходит в Manager-подобные API (и свои read-эндпоинты) — это держит «внешний» интерфейс стабильным, если когда-то UI станет отдельным SPA.

---

## 3. Минусы раздельного существования

1. **Сложность запуска/эксплуатации:**
   - Нужно поднимать **два процесса** (два терминала/службы), следить за порядком. Уже было недопонимание: «WebUI же вместе с Manager запускается» — это не так.
   
2. **Двойная БД-логика и риск рассинхронизации:**
   - Manager пишет через SQLAlchemy, WebUI читает/пишет тем же файлом через raw sqlite.
   - Разные пути к БД и разные стили доступа — риск конфликтов блокировок SQLite (ecли появятся записи из UI), рассинхронизации схемы, дублирования «форматов ответов».
   - Пример: WebUI дублирует формат ответов Manager'а (`/api/audit` у обоих) — расхождение формата легко даёт рассинхрон.

3. **Дублирование кода и конфигурации:**
   - Оба процесса тянут свои настройки (`webui/config.py` vs manager), CORS, подключение к БД.
   - Два места, где надо помнить про `dcap.db`.

4. **Операционные накладные:**
   - Два порта, две health-проверки, два supervisor/systemd-юнита, две точки мониторинга.
   - При контейнеризации — два сервиса в compose вместо одного.

5. **Редирект — хрупкая связка UX:**
   - Переход по `:8000` → редирект на `:8001`; если UI не поднят — пользователь видит ошибку соединения. «Дырка» при частичном старте.

---

## 4. Вариант «слить WebUI внутрь Manager»

Идея: смонтировать `webui.main:app` (или его роутер/статику) как подприложение внутри `manager.src.main:app`, чтобы **один процесс** на `:8000` отдавал и API, и дашборд.

### Реализация (FastAPI)

FastAPI позволяет монтировать подприложение, **но** у вложенного приложения свой `/docs`, своя обработка CORS, своя маршрутизация на том же порту. Наиболее чистый способ — перенести **роутер** WebUI в Manager:

```python
# manager/src/main.py
from webui.api.routes import router as webui_router
app.include_router(webui_router)   # + монтирование статики/папки webui
```

Либо инъекция через полный mount:

```python
from fastapi.staticfiles import StaticFiles
from webui.main import app as webui_app
app.mount("/ui", webui_app)   # или перенести html-представления прямо в manager
```

Требуется:
- решить конфликт маршрутов API (у Manager и WebUI пересечений почти нет: `api/*` у Manager, `/` + свои `/api/*` у WebUI);
- свести **два пути к БД к одному** (убрать raw-sqlite дубль или перевести WebUI на общий SQLAlchemy `get_db`);
- один CORS-конфиг, одну health-проверку.

### Плюсы слияния

1. **Один процесс / один порт / один запуск:**
   - `python run_manager.py` поднимает и API, и UI. Проще эксплуатация, запуск, деплой.
   - Не нужно держать в голове порядок и «двойной старт».

2. **Одна БД-логика:**
   - Единое подключение (SQLAlchemy), нет дублирующих raw-sqlite чтений и риска рассинхронизации схемы/блокировок.

3. **Меньше накладных:**
   - Одна health-проверка, один CORS, один supervisor/systemd-юнит, один контейнер в compose.

4. **UX без «дырки»:**
   - Нет хрупкого редиректа между портами; `/` сразу отдаёт дашборд.

5. **Проще для операторов:**
   - Всё на `:8000`, один URL для всего.

### Минусы слияния

1. **Потеря масштабирования и изоляции:**
   - UI и API растут/падают вместе. Нельзя реплицировать только UI или только API.
   - Падение(тяжёлый запрос/утечка памяти) в UI-роутах может задеть обработку заданий сканерами/агентами.

2. **Смешение ответственности и зон:**
   - Внутренний API для агентов и публичный UI окажутся в одном процессе/порту.
   - Труднее ограничить доступ (например, UI только для операторов, а API — для агентов).

3. **Раздувание Manager-кода:**
   - ~1265 строк UI-роутов лягут в тот же процесс, что и control-plane. Увеличится поверхность атаки и сложность поддержки.

4. **Миграция и риск:**
   - Нужно аккуратно совместить два набора маршрутов, CORS, статику, шаблоны.
   - Регресс текущего (уже работающего) раздельного запуска. Требует тестов.

## 5. Рекомендация / варианты для архитектора

**Вариант A (компромисс, рекомендуется к обсуждению):** не сливать полностью, но:
- оставить раздельные процессы (**сохранить плюсы 1–5 раздела 2**);
- **устранить главный минус** — дублирование БД-доступа: перевести WebUI с raw `sqlite3` на общий SQLAlchemy `get_db` Manager'а и свести пути к одной БД;
- официально зафиксировать в AGENTS.md/докладе, что WebUI — **отдельный обязательный процесс** на `:8001` (закрыть недопонимание из раздела 3.1);

**Вариант B (полное слияние):** если приоритетом является простота запуска/деплоя и объём системы невелик — монтировать WebUI в Manager (`include_router` + общая БД), оставив **возможность** запустить UI-часть отдельно по флагу (`--no-webui`), чтобы не терять изоляцию при росте.

**Вариант C (промежуточный):** сделать **единый фасад-лаунчер** (`run_all`), который поднимает Manager и WebUI как два процесса из одной команды — сохранить изоляцию, но убрать ручной двойной запуск.

---

## 6. Ключевые факты для решения

- Общая БД уже есть: `manager/dcap.db`. Проблема — **два стиля доступа** (SQLAlchemy vs raw sqlite).
- WebUI сейчас дублирует часть API-форматов Manager'а (см. `/api/audit`).
- Оба компонента уже запускаются единообразно через `run_<модуль>.py`.
- Основная боль раздельного запуска — **не сам процесс, а дублирование БД-логики и недопонимание порядка запуска**.
